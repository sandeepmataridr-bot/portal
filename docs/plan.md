## Context
The existing project at `I:\infusion_server` (Flask/Python, one 4,689-line `app.py`, SQLite + JSON files, no shared layout between pages) is being used **only as a functional/domain reference** — not as code to migrate or preserve structurally. The goal is a ground-up new build with the same core functionality (role-based dashboards for admin/doctor/reception/pharmacy/insurance, patient + infusion management, pump-device sync) plus what the reference lacks: clinical safety interlocks, dosage/rate capping, hardened security, and a real sync/webhook channel to a future Android pump-controller app.

**Core architectural reframing (locked in with the user, this is the most important shift from the reference and from earlier drafts of this plan):**
- Each infusion **machine is a fully autonomous edge controller** — its own local datastore, its own complete control + safety logic (interlocks, dosage caps), and its own credentials/cryptographic identity ("complete keys is with the machine only"). A machine can run a patient's entire infusion indefinitely with **zero network connectivity**; the server being unreachable never stops treatment.
- The **server is a fleet dashboard and the master registry — not the enforcement authority.** Its job: hold the shared, hospital-wide registry of patients/doctors/medicines/insurance (matching the reference's design, e.g. `patients.machine_id` assigns a patient to a machine); give staff one place to monitor every connected machine (live status, infusion progress, cross-role workflows); let staff author records that get synced out to the relevant machine.
- **Sync model = "server proposes, machine decides."** When the server has something for a machine (a newly registered patient, a doctor's order, an updated medicine record), it queues it as a pending proposal. The machine's own local logic — out of scope for this build, it's the separate Android app the user will connect later — validates and accepts, rejects, or modifies it. Rejections are reported back and shown on the dashboard, never silently overridden. The server never holds a master key or credential that could force a machine into a state it didn't locally accept.
- Because machines are expected to be offline for extended periods and likely sit behind NAT/mobile networks, **sync is machine-initiated** (the machine calls home when it gets connectivity — matching the reference's existing WS `connect` + poll pattern), not the server pushing inbound webhook calls to a device it can't reliably reach. "Webhook" in the user's ask is treated here as *guaranteed, queued, at-least-once delivery of change events to whichever machine they belong to, picked up whenever that machine next connects* — this is flagged as an assumption; correct if a literal inbound-webhook-to-device model was intended.
- **The infusion machine has the highest rights and is never remotely controlled by an ordinary sync proposal or by any role below superuser** (re-confirmed explicitly, post-M6) — patient/order/config data is still always a proposal the machine can freely ignore, never a command. **Superseded in one narrow, deliberate case** (see "Super-user remote commands" below): the `superuser` role specifically can send real pause/resume/stop/flow-rate-adjust commands the machine is expected to act on — the one intentional exception to "machine always decides," scoped to the single role built for full accountability and covering emergencies. Every other role, and every other kind of data (patient tags, orders, medicine catalog, doctor roster), stays governed by the original principle: proposal only, never a command.

**Scope boundary (confirmed with the user): this repo is the flow-management website, not machine design/development.** The physical machines (infusion pumps, ECMO, EBOO) are a separate engineering effort with their own device-side control logic and safety enforcement — out of scope here entirely. This website's job is coordination and conflict prevention: keeping the shared registry consistent, enforcing the role hierarchy and workflow order (§ "Strict Role-Based Access & Workflow Enforcement"), and catching/surfacing conflicts in data or treatment across roles and across a patient's multiple simultaneous machines — not commanding the machines themselves. Every design choice so far (server proposes/machine decides, pre-proposal validation instead of live enforcement, ECMO/EBOO as receive-only telemetry sources) already follows from this boundary; this note just makes it explicit for future reference.

Other decisions locked in with the user:
- **Frontend**: React. **Backend**: NestJS (TypeScript).
- **Historical data**: start clean, no migration from `pharmacy.db`/`patient_data/*.txt`.
- **Hosting**: Cloud VPS → Redis/BullMQ is fine to use for the sync/webhook delivery worker.
- **Interlocking + capping** = clinical safety interlocks (cross-role validation chains) + hard dosage/rate caps — now understood to be enforced primarily *on the machine*, with the server doing pre-proposal validation and post-hoc reporting/mirroring for dashboard visibility and audit, not live control.

## Synopsis
A fleet-based hospital infusion management platform. Physical infusion pump devices (Android-controlled, connected later) run fully autonomously at the bedside — their own local data, their own complete safety/control logic, their own credentials — and never depend on the server to treat a patient. A NestJS + React server is the fleet's dashboard and master registry: staff (admin/doctor/reception/pharmacy/insurance) manage patients, orders, medicines, and insurance claims from role dashboards, and see live status across every connected machine. Server→machine data moves as sync proposals a machine can accept or reject; machine→server data moves as reported outcomes. The system stays fully functional at the bedside through network loss and reconciles automatically on reconnect.

## Flow

**A. Staff / server-side**
1. Staff logs in (JWT) → routed to a role dashboard (admin/doctor/reception/pharmacy/insurance).
2. Reception registers a patient → record created in the shared Postgres registry.
3. Doctor or reception tags the patient to a specific machine (`patients.machine_id`).
4. Doctor authors an infusion order (steps: medicine, rack/channel, volume, rate) → server runs pre-proposal validation (structural + dosage-cap checks) → queued in `sync_outbox` for that machine.
5. Pharmacy manages inventory / medicine requests; insurance reviews claims — same shared-registry + role-dashboard pattern.
6. Dashboard shows live fleet state: total machines registered vs. currently connected, each machine's assigned patient and live infusion status, and the sync status (pending/accepted/rejected) of anything proposed to it.

**B. Machine / edge side**
1. Machine boots and runs independently on local data + control logic — no server dependency to treat a patient.
2. When network is available, it connects to the server (WebSocket, authenticated with its own credentials — never a server-held master key).
3. On connect: pulls everything queued in `sync_outbox` since its last acknowledged version, accepts/rejects each locally.
4. Pushes back anything it did since the last sync (completed steps, live status, local safety rejections) → recorded in `sync_inbox_log`, reflected live on the dashboard.
5. If disconnected again, it keeps operating from local state; the next reconnect repeats the pull/push cycle — nothing is lost, nothing requires the server to be reachable in between.

## Architecture

**Monorepo** (pnpm workspaces + Turborepo):
```
infusion-platform/
  apps/api/                 # NestJS backend (fleet dashboard + registry + sync hub)
  apps/web/                 # React (Vite) frontend
  packages/shared-types/    # zod schemas shared by API DTOs, React forms, and the machine sync contract
  infra/docker/
  docs/adr/, docs/sync-contract.md   # the machine-sync protocol doc, this project's equivalent of a webhook contract
```

**Data**: Postgres + Prisma. Core reference-derived tables (`users` replacing the doctors/users.json split, `patients`, `medicines` with new `max_flow_rate_ml_per_h`/`max_single_dose_ml`/non-overridable `absolute_max_flow_rate_ml_per_h`, `insurance_claims`, `medicine_requests`, `audit_logs`, etc.) plus the new infusion tables (`infusion_orders`, `infusion_steps`, `infusion_step_events`, `infusion_live_status`) as first-class rows instead of `.txt` files.

**New: sync/proposal tables** (the actual core of this system given the offline-first model):
- `machine_credentials` — hashed, rotatable per-machine secret/keypair reference. The server stores only what it needs to *verify* a machine's identity, never a value that could be used to impersonate it.
- `sync_outbox` — every server-side change to a machine-owned entity (patient, order, medicine update) writes a row here **in the same DB transaction** as the change: `id`, `machine_id`, `entity_type`, `entity_id`, `payload`, `version`, `status` (pending/delivered/acked/rejected/superseded), `created_at`. This is what a machine pulls (or gets pushed over an open socket) when it connects.
- `sync_inbox_log` — append-only record of what each machine has reported back (accepted/rejected a proposal, or pushed its own locally-originated change, e.g. a completed infusion step) — the audit trail for "what did the machine actually do," independent of what the server proposed.
- Every machine-owned entity (`patients`, `infusion_orders`, `infusion_steps`) carries a `version` and a `sync_status` (`pending_machine_ack` / `accepted` / `rejected`) so staff can see on the dashboard whether a given order has actually reached and been accepted by the device treating that patient — not just "saved on the server."

**NestJS modules**: `AuthModule`, `UsersModule`, `PatientsModule`, `MachinesModule` (registry, credentials, connection/session tracking), `MedicinesModule`, `MedicineRequestsModule`, `InsuranceModule`, `InfusionsModule` (order/step data model + **pre-proposal** validation), `SyncModule` (outbox/inbox, delta-sync endpoints, WS gateway for connected machines), `AuditModule`. RBAC via a global, deny-by-default `RolesGuard`.

**Machine visibility & patient-machine tagging**: `MachinesModule` tracks every registered machine plus its live connection state (WS-connected, last poll/seen, offline duration), so the dashboard always shows *N total machines, M currently connected* — this is the core "monitor what's happening inside" view the user asked for. Both the **doctor** and **reception** roles are authorized to tag/reassign a patient to a machine (not admin-only).

**Multiple machine types, multi-machine patients (added after initial approval).** The fleet isn't infusion-pumps-only — it also connects ECMO and EBOO devices, each independent. This changed two things from the first draft of this plan:
- **Machine gains a `machineType`** (`INFUSION_PUMP` | `ECMO` | `EBOO`, extensible). The `Machine` model stays deliberately type-agnostic (registration, connectivity, credentials only); each machine type gets its own domain module with its own typed order/step/live-status tables and state machine — `InfusionModule` is the first and only one fully built so far, per the user's "framework now, specifics later" call. ECMO/EBOO get their real clinical data modeled once specified.
- **Patient↔Machine is many-to-many**, not the reference's single `machine_id` FK — a patient can be on ECMO and an infusion pump simultaneously. This is a `PatientMachineAssignment` join table (patient, machine, assigned-by, assigned/unassigned timestamps, sync status), and `InfusionOrder`/`InfusionLiveStatus` now reference a specific `machineId` directly rather than inferring it from the patient.
- **Sync directionality is per machine type**: `INFUSION_PUMP` is bidirectional (the full "server proposes, machine decides" model). `ECMO`/`EBOO` are **unidirectional** — they only ever push telemetry to the server (operated directly at the bedside, never remotely commanded), so the server never queues `sync_outbox` proposals for them, and a patient-machine assignment for these types is just server-side bookkeeping, treated as immediately accepted.

**Clinical interlocks & capping — reframed role.** The `InfusionStepStateMachine` and `InfusionCapService` still exist server-side, but their job changes:
1. **Pre-proposal validation** — before the server ever queues an order/step as a proposal for a machine, it runs the same structural + cap checks (shared zod schema with the frontend) so staff get fast feedback and obviously-invalid data never even reaches the device.
2. **Mirroring/recording** — when a machine reports back what it actually did (accepted, rejected, ran with a modification, hit a local safety block), the server records that transition in `infusion_step_events`/`sync_inbox_log` and reflects it on the dashboard — it does not re-derive or override the machine's decision.
3. **The live, real-time enforcement path (can't start until dual-confirmed, hard reject over cap, etc.) is the Android app's responsibility, out of scope for this build.** This plan's `docs/sync-contract.md` should specify the *shape* of proposals and reports precisely enough that the Android team can implement matching enforcement, but this repo does not implement device-side control logic.

**Security**: argon2id password hashing; JWT access + rotating refresh tokens (per-role revocation, unlike the reference's doctor-only revocation); env-var secrets validated at startup; `@nestjs/throttler`; explicit CORS allow-list; TLS via reverse proxy on the VPS; `machine_credentials` hashed + rotatable, HMAC-signed sync requests with a replay window, **hard 401 when no credential exists** (direct fix for app.py:3759–3761, where a missing key silently means "authorized"); global `ValidationPipe`, Helmet, structured logging with PII/PHI redaction.

**Sync channel (the "webhook" ask)**: machine-initiated connection (WebSocket when live, REST delta-sync poll otherwise) — mirrors and extends the reference's `connect` handler (app.py:1004–1021) and `/api/sync/*/delta` pattern. On connect, a machine: (1) pulls everything in `sync_outbox` addressed to it since its last acked version, (2) pushes its own accumulated local changes since the last successful sync, each becoming a `sync_inbox_log` row and updating the relevant entity's `sync_status`. A Redis/BullMQ worker manages retry/backoff for proposals that fail delivery or go unacked, and connection-state tracking in `MachinesModule` lets the dashboard show each machine as online/offline/last-seen — this is the primary "monitor what's happening inside" view the user described.

**Frontend**: Vite + React + TypeScript, role-based routed dashboards under one shared `AppShell`, TanStack React Query with WS-driven live updates, React Hook Form + shared zod schemas. The machine/fleet view is a first-class screen: per-machine online status, currently-assigned patient, live infusion status, and sync health (any proposals stuck pending-ack).

**Patient Timeline component** (reused, not rebuilt per page) — the reference's versioned patient-history feed (seen in `reception.html`'s and `insurance.html`'s "Patient Details" modal) is preserved as a shared React component, not just a reception-only feature. It renders one entry per version with an action badge and type-specific detail rendering, matching the exact action set already catalogued from the reference: `REGISTER`, `READMIT`, `READMIT_UPDATE`, `DISCHARGE`, `DOCTOR_UPDATE`, `DOCTOR_SUGGESTION`, `DOCTOR_SUGGESTION_DELETED`, `INSURANCE_APPROVED`, `INSURANCE_PARTIALLY_APPROVED`, `INSURANCE_REJECTED`, `INSURANCE_REVOKED`, `INSURANCE_DOCUMENTS_REQUIRED` — each with its own badge color and layout (e.g. `DOCTOR_SUGGESTION` renders a medicine table, `INSURANCE_*` renders status/remarks/approver). The component takes an optional action-prefix filter so reception shows the full timeline, insurance shows only `INSURANCE_*` entries, and doctor emphasizes `DOCTOR_*` entries — one implementation, filtered per role rather than duplicated per page.

**Machine status on every role dashboard, not just the fleet screen** — the stat-card row pattern from `reception.html` ("Today's Patients", "Insurance Pending", "Approved", "Rejected", "Discharged") gets a live machine-status tile (e.g. "Machines Online: M/N") added alongside the existing role-specific stats, sourced from `MachinesModule`'s connection tracking. Any role landing on their dashboard sees pump connectivity health immediately, without navigating to a separate fleet view — the dedicated fleet/machine screen remains for the detailed per-machine drill-down (assigned patient, live infusion status, sync health).

## Strict Role-Based Access & Workflow Enforcement
Two distinct guarantees, both enforced **server-side** — never just hidden in the UI, since a medical system can't rely on staff not clicking the wrong button.

**1. Role permission matrix (hierarchy)**
- `admin` — full account/config management (create/deactivate users of any role, rotate machine credentials, rack settings); can view everything fleet-wide; can perform overrides, but every override is a named, reason-required, audited action — never a silent bypass of another role's boundary.
- `doctor` — owns clinical authorship: patient vitals/diagnosis edits, infusion order creation, medicine suggestions/requests, tagging a patient to a machine. Cannot manage other doctor accounts, cannot verify/dispense pharmacy stock, cannot decide insurance claims.
- `reception` — owns patient lifecycle: register/readmit/discharge, tagging a patient to a machine. Cannot author clinical orders, cannot touch pharmacy inventory or insurance decisions.
- `pharmacy` — owns inventory + dispensing: stock in/out, medicine catalog/caps, verifying and fulfilling doctor orders and medicine requests. Cannot edit patient clinical data or insurance decisions.
- `insurance` — owns claims: approve/partial/reject/request-docs/revoke. Read-only on patient clinical data; no write access anywhere else.
- No role has default access to another role's write endpoints. The deny-by-default `RolesGuard` (§ NestJS modules) is the mechanism; this matrix is the policy it encodes — every controller route is checked against it in review, not left to an undecorated default.

**2. Workflow order (cannot be skipped — checked at the service layer, not just implied by page order in the UI)**
- A patient must exist (reception) before a machine can be tagged to them (doctor or reception) before a doctor can author an infusion order for them — each precondition is a service-layer check, not just a disabled button.
- An order can't leave `DRAFT` without ≥1 step on an active medicine; can't reach `READY` for a high-alert medicine without a second, distinct confirmer; can't reach `RUNNING` until pharmacy verification matches the ordered medicine and volume exactly (§ Clinical interlocks).
- A stock-out transaction referencing a patient must reference a step that has actually passed pharmacy verification — pharmacy cannot dispense against an order that doesn't exist or hasn't been through a doctor.
- An insurance claim can only be created for a patient with `insured = true` and policy details on file; claim status can only move through the defined sequence (Draft → Submitted → Under Review → {Approved | Partially Approved | Rejected | Documents Required}), and only `Partially Approved`/`Rejected` can be revoked back to `Under Review` — no arbitrary status jumps.
- Every skip-attempt returns a typed 409 with a specific error code (not a generic failure) and is written to `audit_logs` — an attempted shortcut is visible and traceable, not just silently blocked.

## M7 — Bedside (machine-originated) patient/order creation

### Context
The Android pump-controller app (built in a separate session, `InfusionApp2`) surfaced a real gap while mapping the sync contract: today the *only* two machine-reachable endpoints in the whole API are `POST /sync/pull` and `POST /sync/push`, and `push()` can only **update** an entity the server already knows about (`updateMany({where:{id: report.entityId}})` silently matches zero rows for anything the server never created) — there is no way for a machine to originate a new `Patient` or `InfusionOrder` that reaches the shared registry.

Confirmed directly with the product owner that this is a real, intended second creation path, not just a bug to patch:

- **Two ways a patient/order comes to exist**: (A) reception/doctor author via the dashboard, synced *down* to the machine as a convenience — "server sends data to reduce data entry time in the machine," staff at the bedside can choose to pull this instead of typing it fresh. (B) staff at the bedside turns the machine on directly, picks "add new patient" or "select existing," enters basic data + infusion config, and runs it — fully offline-capable — and if/when connected, this syncs *up* and becomes a real registry record, with live status (flow rate, dispensed volume, pump state) also syncing up.
- **The server's role for path (B) is purely observational**, never gating: *"machine side is always correct. server is only for showing what is going on in the machine."* Cap/workflow validation for machine-originated orders becomes a recorded flag for dashboard visibility, never a rejection of what the machine already ran — this is consistent with, not a change to, the already-locked "pre-proposal validation only, never live enforcement" principle above; it just extends that principle explicitly to the upward direction.
- **"Select existing patient" at the machine is scoped to that machine's own `PatientMachineAssignment` history** — not the full hospital roster (PHI exposure concern for a shared bedside device). This already fits the existing per-machine sync-addressing model without new plumbing.
- **Bedside-created records are attributed to the machine's own credential**, not a per-staff login — no new bedside auth surface. `AuditLog`/`PatientHistory` need a machine half added to their actor concept (today only `InfusionStepEvent` has both `actorType`/`actorMachineId`; confirmed by reading the schema — `AuditLog` and `PatientHistory` don't yet).
- **Duplicate patients** (bedside-created, turns out to already exist from reception) get flagged into a manual reception review queue — never auto-merged, never blocking the machine.

### Pre-existing UI completion gaps found while re-checking the flow (M1–M6, not M7 scope — fix regardless)

Not new scope — these are real holes in the already-shipped app, found by systematically walking every dashboard against every backend route. **Most severe first:**

- **The infusion-step lifecycle cannot complete through the UI at all.** `InfusionsService.submitOrder` moves every step straight to `PENDING_PHARMACY_VERIFICATION` (verified directly in the code). `useVerifyStep` (`apps/web/src/features/infusions/api.ts`) exists but is imported by zero components — `InfusionStepsPanel.tsx`'s `StepActions` only handles `PENDING_SECOND_CONFIRMATION`/`READY`/`RUNNING`/`PAUSED`, falling through to nothing for the pharmacy-verification status every order actually starts at. Every order created via the doctor's `CreateOrderModal` today dead-ends here permanently — no dashboard user, in any role, can move it forward. This is the most severe finding in this whole review.
- **`reject`, `cancel`, and `override` (the admin cap-override escape hatch) have no hooks and no UI at all** — not even dead code, unlike the above. Contrast with `confirm-high-alert`/`start`/`pause`/`resume`/`complete`, all correctly wired.
- **Machine tagging has no UI anywhere** (detailed in §7a below) — `InfusionsService.createOrder` itself throws *"Patient is not currently assigned to this machine — tag the machine first"* (verified) when untagged, and there is no button anywhere that lets any role fix that.

All three block the same core loop: tag → author order → verify → run. Fixing them is wiring existing, already-tested backend logic to existing hook patterns (`useVerifyStep`/reject/cancel/override all follow the exact same shape as the five actions already wired in `StepActions`) — not new design work, should be quick relative to M7's actual new scope. Recommend doing this **before** M7, not after — no point adding machine-originated orders to a lifecycle that can't complete for dashboard-originated ones either.

### Immutable audit trail — confirmed requirement, three real gaps found

This is a medical device — the complete history of every patient, every configuration, every step transition, every flow-rate adjustment must be a permanent, admin-readable, **admin-cannot-modify** log. Checked precisely rather than assumed: `AuditLog`, `InfusionStepEvent`, `SyncInboxLog`, and `PatientHistory` already have zero `.update()`/`.delete()` calls anywhere in the API (verified by grep) — insert-only by convention today, which already covers patient creation, every step transition (started/completed/moved to next step), and every machine report. Three real gaps against the full requirement:

1. **Flow-rate/telemetry history isn't actually logged — only the current value.** `InfusionLiveStatus` is one row per machine (`machineId` unique), overwritten on every update — by original M7 design, deliberately "current-snapshot only" for the live dashboard view (see §5 above). That's the wrong shape for a permanent log: a rate adjustment mid-run with no step-status change would silently overwrite the prior value with no record it happened. **Fix**: add an append-only `InfusionTelemetryLog` (`id`, `machineId`, `stepId?`, `flowRateMlPerH`, `dispensedVolumeMl`, `remainingVolumeMl`, `pumpState`, `recordedAt`, `receivedAt`) written *alongside* the existing `InfusionLiveStatus` upsert on every machine telemetry report (§3/§5) — the upsert stays for "what's happening right now," the log is the permanent record of every value it ever held.
2. **Step configuration isn't captured in an immutable entry.** `AuditLog`'s `INFUSION_ORDER_CREATED` entry today only records `{patientId, machineId, stepCount}` (verified in `infusions.service.ts`) — not the actual medicine/volume/rate configured, which only lives in the current (not currently update-guarded) `InfusionStep` row. Fix: populate `AuditLog.after` with the full step configuration array on order creation, mirroring how `PatientHistory.snapshot` already captures a full patient snapshot rather than a summary.
3. **No unified view, and immutability is convention, not a guarantee.** Checked every `@Get` audit/history route in the API — only two exist (`GET /medicines/audit`, `GET /doctors/:id/history`), nothing that stitches `PatientHistory` + `InfusionStepEvent` + `SyncInboxLog` + the new telemetry log into one timeline per patient or per machine. Fix: new `GET /patients/:id/audit-trail` and `GET /machines/:id/audit-trail` (`@Roles('admin')`, read-only — no corresponding write/update endpoint should ever exist for these tables), merging all four sources chronologically. For the "admin cannot modify" guarantee to be real rather than incidental, add Postgres-level enforcement, not just the absence of application code: a `REVOKE UPDATE, DELETE` on these four tables (plus the new telemetry log) for the app's own DB role, so even a future bug or a direct psql session under that role physically cannot alter history — only `INSERT` and `SELECT` remain possible.

### Design

**0. Module-split prerequisite.** `SyncService` needs to call into `PatientsService`/`InfusionsService` to reuse their create logic rather than duplicating it. Today `InfusionsModule` and `MachinesModule` both import `SyncModule`, and `PatientsModule` imports `MachinesModule` — so `SyncModule` importing `PatientsModule`/`InfusionsModule` back would cycle (verified by reading all four `*.module.ts` files). Fix: split `SyncModule` — extract a `SyncOutboxModule` owning `SyncOutboxService`, `SyncGateway`, `SyncDeliveryProcessor`, `MachineCredentialsService`, `MachineAuthGuard` (exactly what's exported/consumed outside the sync folder today). `InfusionsModule`/`MachinesModule` depend on `SyncOutboxModule` instead of `SyncModule`; `SyncModule` becomes a top-level consumer importing `SyncOutboxModule` + `PatientsModule` + `InfusionsModule`. No cycle, no `forwardRef`.

**1. Schema changes** (`apps/api/prisma/schema.prisma`, one migration):
- Attribution: add `actorMachineId` to `AuditLog`, and `actorType`/`actorMachineId` to `PatientHistory` (mirrors the pattern `InfusionStepEvent` already has). "Exactly one of user/machine set" enforced at the service layer, same as every other cross-entity precondition in this schema.
- Origin markers, mirroring the existing `registeredById`/`registeredBy` pattern: `Patient.registeredByMachineId`, `InfusionOrder.orderedByMachineId` (requires making `orderedById` nullable), `PatientMachineAssignment.assignedByMachineId`.
- **Loosen `Patient` for the bedside minimal-identity path — flag this one explicitly, it's a real integrity trade-off, not cosmetic**: `mobile`, `emergencyContact`, `aadhar` → nullable; `ipNumber` → nullable (stays `@unique`, Postgres allows multiple `NULL`s). Add `Patient.roomOrBed String?` and `Patient.needsReceptionCompletion Boolean @default(false)`. The reception-authored path stays fully protected because `registerPatientSchema` (the Zod API boundary) is untouched and still requires these fields for that path — only the DB-level guarantee loosens, consistent with this schema's existing "enforce at the service/validation layer, not the DB" philosophy, but worth your explicit sign-off since it does weaken what the table itself guarantees.
- Medicine identity fallback on `InfusionStep`, mirroring the exact pattern `MedicineRequest` already uses (`medicineId String?` + required fallback name): `InfusionStep.medicineId` → nullable, add `medicineNameRaw`/`concentrationRaw String?`, exactly one of `medicineId`/`medicineNameRaw` enforced at the service layer.
- Live telemetry needs **no schema change** — `InfusionLiveStatus` already has `flowRateMlPerH`/`dispensedVolumeMl`/`remainingVolumeMl`/`infusedTimeMin`/`pumpState` (unique per `machineId`); just needs a machine-reachable write path.
- New `ReconciliationItem` model (kind: `patient_duplicate` | `medicine_match`, status: `pending` | `resolved`, `machineId`, `entityType`/`entityId` of the bedside-created record, `rawPayload`/`candidates` as `Json` matching how `SyncOutboxEntry.payload`/`InfusionStepEvent.payload` already use `Json` for flexible data, `resolvedById`/`resolution`). One shared mechanism for both patient dedup and medicine-name matching rather than two.
- **Machine-created temporary doctors (emergency, offline case)**: confirmed use case is a bedside doctor not already in the machine's synced roster (on-call/substitute, no network to look them up first) — a lightweight reference, explicitly **not** a login-capable account. Maps onto the existing `DoctorProfile` model rather than a new one: `DoctorProfile.userId` → nullable (was required — every real doctor account is 1:1 with a `User` today), add `DoctorProfile.isTemporary Boolean @default(false)` and `DoctorProfile.createdByMachineId String?`. `Patient.doctorProfileId` already just points at any `DoctorProfile` row, real or temporary — no change needed there.

**2. Sync contract** (`packages/shared-types/src/sync.schema.ts`): keep additive to the existing `syncReportSchema` shape.
- New `SYNC_REPORT_OUTCOMES` value `'reported'` — meaning "machine-originated, no prior proposal, this is simply what exists/happened," distinct from `accepted`/`rejected`/`modified` (all specifically about responding to a server proposal). `proposalId` absence + `outcome: 'reported'` is the discriminator — no separate report-type field needed, reusing what the contract already implies (`docs/sync-contract.md` already documents `proposalId` absence this way).
- New `SYNC_ENTITY_TYPES` value `infusion_live_status` for telemetry (always `outcome: 'reported'`, keyed by the report's `machineId` since `InfusionLiveStatus.machineId` is already unique — no time-series table, current-snapshot only, matching "server is only for showing what is going on now").
- New `SYNC_ENTITY_TYPES` value `doctor` for the emergency temporary-doctor case (always `outcome: 'reported'`) — payload `{name, qualification?, specialty?}`.
- **`pull()` gains a reference-data payload, not just proposals.** Today `SyncPullResponse` is only `{proposals, latestVersion}` (verified in `sync.service.ts`) — proposals already deliver patient data scoped correctly (a tag event enqueues that patient's data, so the machine only ever learns about patients actually assigned to it), but there's no channel at all for the doctor roster. Add `SyncPullResponse.doctors: Array<{id, name, qualification, specialty}>` — the current active-doctors list (small, slow-changing, hospital-wide — deliberately *not* scoped per-machine like patients are, since any doctor might need to be attributed on any machine), sent on every pull rather than versioned/delta'd given its size. **Explicitly confirmed out of scope for `pull()`**: a patient's full historical infusion record (past completed orders from earlier admissions) — the machine only ever receives current/pending data, never the archive.
- **Client-minted UUIDs**: the Android app generates the Patient/InfusionOrder/InfusionStep id locally at creation and reuses it in every subsequent report — document this as a real behavioral requirement, not just a server detail.
- Add a batch result response (`syncPushResponseSchema` with per-report `status: 'ok'|'error'`) — `push()` today returns only `{received: number}`, giving the app no way to know which report in a batch failed. This also matters because creates are more failure-prone than the current pure-update no-ops.
- **Open naming question, don't silently decide**: `entityType: 'patient'` already means "ack of a `PatientMachineAssignment`" in the existing accepted/rejected path — reusing the same string for "brand new `Patient` row" (disambiguated only by `proposalId`/`outcome`) avoids type sprawl but is a subtle overload. Confirm this reading is acceptable.

**3. `SyncService.push()`**: wrap each report in its own try/catch + transaction (fixes a real *pre-existing* bug too — today one bad report mid-batch throws and aborts the whole request after earlier reports already wrote non-transactionally). Dispatch `outcome === 'reported'` reports by `entityType` to new, dedicated methods (not inlined in `SyncService`):
- `PatientsService.registerFromMachine(...)` — idempotent on the client-minted `entityId` (a retried push after a dropped connection must not double-create or error), sets `registeredByMachineId`/`needsReceptionCompletion: true`, writes `PatientHistory` v1 with the machine actor, runs `ReconciliationService.findPatientDuplicates(...)` (hospital-wide search — a different, wider scope than the machine's own "select existing" picker, which stays scoped to that machine's assignment history) without ever blocking the create.
- `InfusionsService.createOrderFromMachine(...)` — same idempotency requirement; creates the order + steps with client-minted step ids; for steps with a resolved `medicineId`, still runs the existing `InfusionCapService` check but only to **record** the result on `InfusionStepEvent.payload`, never to throw; unresolved medicine names go to the reconciliation queue. **Assignment handling must reuse `assignPatientToMachine`'s existing invariant, not a bare upsert**: if the machine's active assignment is already this patient, no-op (idempotent, matches the existing method's own behavior); if it's a *different* patient, explicitly close out that row (`unassignedAt: now`) before creating the new one — never leave two active assignments on one machine. Getting this wrong silently breaks the "at most one active assignment per machine" invariant the schema comment already documents.
- `InfusionStepStateMachineService` gets a new `recordMachineReport(...)` method (small refactor: extract the existing `transition()`'s write logic into a private helper) that **skips** `assertStepTransition` — an offline machine may legitimately report `DRAFT → COMPLETED` in one shot — while still writing the same step-update + event-write shape with a machine actor. `transition()` itself is untouched and still enforces the state machine for staff-driven paths.
- `infusion_live_status` reports are a straight `upsert` keyed on `machineId` — simple enough to stay inline in `SyncService`, no new service method — but see §5, this write path now also needs to broadcast over WS.
- `'doctor'` → new `DoctorsService.createTemporaryFromMachine(...)`, same idempotency-on-`entityId` requirement as the other creates. Creates a `DoctorProfile` with `userId: null`, `isTemporary: true`, `createdByMachineId`. **Assumption to confirm on review**: admin can later "promote" a temporary doctor into a real account (new `POST /doctors/:id/promote` — generates login credentials the same way `DoctorsService.create()` already does, sets `userId`/`isTemporary: false`) rather than temporary doctors being permanently reference-only. If temporary should mean *never* promotable, drop the promote endpoint and it stays a pure historical/attribution record.
- Every new/existing staff-facing method signature (`AuthenticatedUser`-typed) stays byte-for-byte unchanged; only the new machine-flavored methods take a `{machineId, machineCode}` actor. This keeps every existing dashboard code path untouched.

## Super-user role + live machine-mirror view

Two related asks, confirmed: (1) one login with full access to every other role's work, with every action still attributed to the real person, not anonymized behind the role it's acting as. (2) A web view that visually mirrors the actual machine's running screen, live, for any machine an authorized user picks.

### 1. Super-user role
New `Role` enum value `superuser` — deliberately **not** an extension of `admin` (confirmed): admin manages accounts/machines/config; superuser does everyone's day-to-day clinical/financial work. Keeping them distinct keeps "who manages the system" and "who's covering someone's shift" separately auditable.
- `RolesGuard` (`apps/api/src/auth/guards/roles.guard.ts`) gets one bypass: if `user.role === 'superuser'`, allow regardless of the route's `@Roles(...)` list. This is the only backend change needed for access — touching every controller's decorator list individually would be far more invasive for the same result.
- **Attribution is already correct, confirmed by re-reading the pattern**: every existing service logs `actorUserId: actor.id` / writes `actedBy: actor.loginId` using the real authenticated user's own id/login — never a role label. A superuser's actions already show up under their own real identity in `AuditLog`/`PatientHistory`, not as "reception." No change needed there beyond what §"Immutable audit trail" above already fixes generally.
- Web: new `SuperUserDashboard.tsx` — a top tab bar (Reception · Doctor · Pharmacy · Insurance · Admin) that renders the *existing* dashboard component for whichever tab is active (`ReceptionDashboard`, `DoctorDashboard`, etc. — reused as-is, not rebuilt). `HomeRedirect.tsx`'s role→route map gets a `superuser: '/super'` entry.

### Super-user remote commands — pause / resume / stop / flow-rate adjustment

The one deliberate exception to this whole plan's "machine always decides" principle. Built with the weight that implies, per your confirmed answers:

- **Online-only, never queued.** A command is only sendable while `SyncGateway.isConnected(machineId)` is true (already-existing method, `sync.gateway.ts`). If the machine isn't currently WS-connected, the control is disabled in the UI with a plain "machine offline — cannot send command" state — never silently queued to apply whenever it next reconnects, which could be dangerously stale by then.
- **New real-time command path, distinct from the proposal/report model everywhere else in this plan.** `POST /machines/:id/commands` (`@Roles('superuser')`) — validates the command (see caps below), then `gateway.emitToMachine(machineId, 'machine.command', {commandId, type, payload})` over the existing WS gateway. This is NOT a `SyncOutboxEntry` — outbox proposals are things the machine can freely ignore forever; a command needs an immediate, real-time acknowledgment, not "delivered, someday."
- **New `MachineCommand` model — `commandType` is a free string, not a Prisma enum, and the endpoint is gated to `machineType === 'INFUSION_PUMP'` for now.** ECMO/EBOO are confirmed coming later, with their own command vocabularies (and possibly no remote-command capability at all — ECMO in particular is high-stakes enough that whether it ever gets this feature is a separate decision, not an assumption). Locking `commandType` to a Prisma enum (`PAUSE`|`RESUME`|`STOP`|`ADJUST_FLOW_RATE`) would mean a schema migration every time a new machine type's command set is defined — exactly the mistake `Machine.machineType` itself already avoids (see the schema comment: free string, framework now, specifics later per machine type). Fields: `id`, `machineId`, `commandType String`, `payload Json?`, `issuedById` (the superuser's real `User.id` — never anonymized), `issuedAt`, `status` (`SENT`|`ACKNOWLEDGED`|`FAILED`|`TIMED_OUT`), `respondedAt`, `result Json?`. `POST /machines/:id/commands` validates `machine.machineType === 'INFUSION_PUMP'` before accepting anything — a 4xx for any other type today, not a silent no-op — and validates `commandType` against `INFUSION_COMMAND_TYPES` (new export in `packages/shared-types/src/infusion.schema.ts`, the same file that already owns the infusion state machine). When ECMO/EBOO get their own domain module later, they define their own command-type list and reuse this same `MachineCommand` table/endpoint shape rather than forking it. **Insert/status-update only, never deleted** — gets the same `REVOKE DELETE` treatment as the other audit tables above; this is the single highest-stakes log entry in the whole system and must be permanent.
- **Confirmation step before send**: re-enter password (reuses the existing login/password-verification path, not a new mechanism) before a pause/resume/stop/rate-adjust request is actually submitted — makes an accidental click structurally impossible, not just unlikely, matching the weight of directly affecting a running infusion.
- **Flow-rate adjustment reuses the existing `InfusionCapService.check(...)` as a hard gate, not a flag.** This is consistent with, not an exception to, the two-tier model already established everywhere else in this plan: *server-authored* actions (a doctor's order, and now a superuser's remote command) are hard-checked against caps before they're ever sent; only *machine-authored* actions (bedside-originated, per M7 §3) are flag-only, because there the machine — not the server — is the one deciding. A remote command is server-initiated, so it gets the same hard gate `InfusionsService.createOrder` already applies (`BadRequestException` with `CAP_VIOLATION` on a violation) — no new caps logic, just a new call site.
- **Machine-side (Android, different repo/session)**: confirmed this requires genuinely new capability there — nothing today lets the app receive a server command and act on hardware. That session needs to: listen for `machine.command` on its existing WS connection, validate it locally too (never trust the network blindly for a hardware action), call into whatever `HardwareSerialController` already exposes for pause/resume/stop/rate-change, and report the result back (`ACKNOWLEDGED`/`FAILED` with a reason) — this is a real spec item to hand to that session, not a trivial wire-up.

**Production routing-prefix gap, found checking this against the actual deployed Caddy config, not assumed.** `infra/docker/Caddyfile` only routes `handle_path /api/* { reverse_proxy api:3000 }` — everything else falls through to the static web app. The NestJS routes themselves have no prefix (`/sync/pull`, `/sync/push`, `/realtime`), so:
- **Direct-to-container** (local dev, LAN testing against the bare API on its own port): use the bare paths — `http://<lan-ip>:3000/sync/pull`, ws `/realtime`.
- **Through the real production deployment** (behind Caddy/TLS): the app must call `https://<domain>/api/sync/pull`, `https://<domain>/api/sync/push`, and connect the socket to `wss://<domain>/api/realtime` — the same `/api` prefix the browser dashboard already uses, so Caddy's existing strip-and-forward rule routes it correctly. Calling the bare, unprefixed paths against the production domain silently hits the SPA's `index.html` fallback instead of the API — same category of bug as the refresh-cookie-path issue found and fixed earlier in M6, invisible in direct-to-container testing, real in production. The app's base-URL config should support both shapes (a toggle or just two different configured base URLs), not hardcode one.

**Explicitly out of scope for this pass** (do not build against these yet — they don't exist server-side until M7 ships): bedside-originated patient/order creation, machine-pushed live telemetry, temporary doctor creation, the `doctor` reference-data list on pull. The app's role against the current M1–M6 surface is pull-and-report only.
